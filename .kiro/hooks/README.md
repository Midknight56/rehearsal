# Rehearsal hooks

Two standalone hook files in the `kiro/FORMAT.md` shape, copied with this README into `.kiro/hooks/` in the Rehearsal repository. `.kiro/**` is owned by the simulation agent's Kiro CLI session (plan section 10), and the `paired-comparison-and-release` spec keeps the hook files and this README current (plan section 11.1). Command actions only: an agent action injects a prompt and costs credits; a command hook costs none. The hooks implement sections 11.2 and 11.3 of `plans/rehearsal-implementation-plan.md` (revision 2, 2026-11-03) and verification-matrix row 31. Browser journeys (`npm run test:e2e`) are not hooked: writers run them before a UI task is declared done and the reviewer agent runs them at gates.

| File | Entry: fires on | Matcher | Command | Timeout | When observed |
| --- | --- | --- | --- | --- | --- |
| `verify-on-stop.json` | `verify-on-stop`: agent stop (CLI 3.x name `Stop`, *verify*; IDE wording "on agent stop") | none | `npm run verify` = `typecheck` + `test:model` (Vitest over `tests/model` and `tests/comparison`) + `build` | 600 | November 4 |
| `model-tests-on-save.json` | `model-tests-on-save`: file save (CLI 3.x name `PostFileSave`, *verify*; IDE wording "on file save") | `^src/(simulation\|spatial)/` (any file under `src/simulation/` or `src/spatial/`) | `npm run test:model` | 300 | November 4 |

Name note. Plan section 11.2 lists `typecheck-on-save.json` (matcher `^src/.*\.tsx?$`, `npm run typecheck`, 120 s). This package ships `model-tests-on-save.json`, scoped to the two engine folders, in its place: the stop hook already typechecks everything through `npm run verify`, and a save under `src/simulation/` or `src/spatial/` is what can break a hand-calculated fixture. Record the shipped name in the plan's next revision (its section 1 provides for refinements). Do not add a typecheck save hook beside it unless both were observed and the save-time cost of running both was measured and logged.

Package manager note. The plan fixes npm with a committed `package-lock.json` (sections 4 and 16), so both commands are `npm run …`; the `kiro/FORMAT.md` example and the other entries' `pnpm verify` do not apply here. If the integrator's November 4 scaffold decision changes the package manager, change the two command strings in both files before the observation run and log the change.

## Fields marked *verify*

The shape was checked against Kiro documentation summaries dated November 3, 2026, not against the installed Kiro CLI (2.37.0 until the November 4 upgrade to 3.x) or IDE 1.4.62. JSON carries no comments, so the marks live here. Confirm each item on the installed version, write the observed value into the file, and record it in `docs/kiro-log.md`:

- `trigger` values `Stop` and `PostFileSave`: *verify*. They are the CLI 3.x PascalCase names reported in `research/rules-and-credits-check-2026-11-03.md`; the IDE lists its triggers as "on agent stop" and "on file save". If the installed version expects other names, read them from its hook reference, change the value and log the name observed. No other trigger (spec lifecycle, pre-tool, prompt submit) is used by this package.
- `version: "v1"`: *verify* the schema version string.
- `matcher`: *verify* whether it is a regular expression (as in the `kiro/FORMAT.md` example) or a glob, and whether it is matched against a workspace-relative path (the pattern assumes it). The glob forms of the same rule are `src/simulation/**` and `src/spatial/**`; if the installed version takes one glob per entry, split the file into two entries with the same command.
- `timeout`: *verify* that the field exists and that its unit is seconds.
- `action.type: "command"` and `action.command`: *verify* the field names, and that the command runs from the root of the checkout the session is open in (where `package.json` is). Rehearsal's Kiro sessions run in the main checkout; fleet worktrees (`../Rehearsal-<module>`) share the same `.kiro/` only after it is merged to `main` and the worktree branch is rebased on it.
- Whether the Kiro IDE reads standalone `.kiro/hooks/*.json` files at all, or only hooks created in its own panel: *verify*, and only if the builder uses the IDE for any Rehearsal session; the planned surface is the Kiro CLI 3.x. An IDE observation does not stand in for the CLI one, or the reverse.

## Observation before citation

A hook is cited in the repository `README.md`, the write-up, the video, the blog post or `docs/kiro-log.md` only after it has been observed firing and the observation is logged (plan section 11.2, matrix row 31). Procedure, due November 4:

1. Scaffold first: `npm run verify` passes from a terminal on `main` (the R0 scaffold), even with few tests. The save hook needs a file to match: `src/simulation/` and `src/spatial/` receive their stub modules (`src/simulation/heap.ts`, `src/spatial/grid.ts`, …) from `simulation-contract` task 1 on its branch on November 4, so the save observation runs in that Kiro CLI session right after task 1. At that point `npm run test:model` fails on `not implemented` by design; record that state in the row, and repeat the save observation once on `main` after the November 11 merge so that one passing run is logged as well.
2. Copy `verify-on-stop.json`, `model-tests-on-save.json` and this README into the repository's `.kiro/hooks/`.
3. In a Kiro CLI 3.x session opened at the repository root: save `src/simulation/heap.ts` (or any file under `src/simulation/` or `src/spatial/`) with a whitespace-only change; then ask the agent for a one-line answer and let the turn end.
4. Save `src/domain/scenario.ts` with a whitespace-only change as well and confirm that `model-tests-on-save` does not fire for it; this settles the path-relative matcher semantics. Revert both whitespace changes afterwards.
5. For each hook, record whether it fired, the configured trigger name, the first and last lines of the command output, the duration, and a screenshot of the hook output saved as `docs/acceptance/img/2026-11-04-hook-stop.png` or `docs/acceptance/img/2026-11-04-hook-save.png`.
6. Append one `docs/kiro-log.md` row per hook: the date; `Kiro CLI <version string as printed>` and the model shown in the session; `Setup: hook observation (matrix row 31)`; the hook file and screenshot path; the command and its result as the hook ran it; the credits the turn used; `none` under "what changed because of a failure", or the change made (for example a corrected trigger name).
7. If a hook does not fire: read the trigger names in the installed CLI's hook reference, change the value, repeat steps 3–6 once, and log both attempts. Never guess a third name.
8. Keep only observed hook files in `.kiro/hooks/`; delete an unobserved one rather than keeping it as decoration, and remove its row from the table above in the repository copy of this README.

Rules while the hooks run: a task whose last `npm run verify` did not pass is not finished. On a spec branch where later tasks' tests are still red by design (the first task of every spec scaffolds failing tests), the stop hook's failures are expected until the spec's last task, and the task's own `Verify:` line is its acceptance; `main` always passes. A failing hook run on `main` is a defect to log and fix, never a reason to disable the hook, raise its timeout, skip a test, widen a tolerance, weaken `npm run verify` or edit `.kiro/hooks/**` from a fleet worktree. `tests/model` stays under 60 s (`simulation-contract` Requirement 10.10) so the save hook stays tolerable; if it still makes editing intolerable, remove the save hook and keep the stop hook rather than loosening `npm run test:model`. `npm run verify` must finish inside the 600 s timeout on the builder's named laptop; shorten the suite rather than raising the timeout.
