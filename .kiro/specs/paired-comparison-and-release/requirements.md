# Requirements Document

## Introduction

`paired-comparison-and-release` is the Kiro-owned second half of Rehearsal's model: it turns two validated scenarios and the engine's `RunResult`s into an honest paired comparison (30 replications with common random inputs, paired differences, an empirical range with a fixed label, improvement counts from actual results, a population-change guard, an assumptions diff), produces every export (re-importable scenario JSON, CSV with `escapeFormulae`, the xlsx assumptions workbook, the printable comparison and the one-page run sheet), and carries the repository's Kiro configuration and release evidence. It serves the organizer reading the Compare and Print screens (built in `src/ui/` by `scenario-editor-and-replay`) and the judge who opens the deployed build without an account, and it records verification-matrix rows 23–31. It implements plan sections 7 (paired comparison), 8 (Compare, Print and export), 9 (privacy and resilience), 11 (Kiro surface) and 15 (release and judge access) of `plans/rehearsal-implementation-plan.md` as spec 11.1 `paired-comparison-and-release`, on branch `kiro/paired-comparison-and-release` under a 350-credit cap. Kiro does every task of every spec (`.kiro/steering/revision-2026-11-16.md`); the run order is the owner's, in `docs/DECISIONS.md`, and dates in older copies of this file are void. Code lives in `src/comparison/` and `src/exports/`; tests in `tests/comparison/`; the repository's `.kiro/` configuration (steering, hooks, the three specs; `.kiro/settings/mcp.json` is written only by the owner's helper) is kept current by this spec; release documents in `docs/third-party-notices.md`, `docs/performance.md` and the README model-limits section.

Terms used below: "the engine" is spec `simulation-contract` (`simulate`, `validateScenario`, `scenarioHash`, `createPathCache`, `MODEL_VERSION`, `MetricValue`, `RunResult`, `Trace`, the worker adapter `SimulationClient`); `H` is `scenario.horizonMs`; "the three Harbor Hall scenarios" are `baseline`, `plusOneCheckin` and `shorterRoute` exported by `tests/model/fixtures/harbor-hall.ts` (tab keys `baseline`, `plus-one-checkin`, `shorter-route`); "the row-1 pair" is `row1Scenario` (one server) as baseline and `row2Scenario` (two servers) as candidate from `tests/model/fixtures/rows.ts`; "code-unit order" is JavaScript string `<` order; "display units" are minutes for windows and horizon, seconds for service, meters for distance, people for counts, `(x,y)` for cells; "the UI spec" is `scenario-editor-and-replay`, whose tasks (also Kiro's) write `src/ui/`, `src/replay/`, `src/imports/`, `src/storage/`, `tests/e2e/` and `tests/video/`. Where a criterion names UI text or a `data-testid`, it is the contract this spec publishes and the UI spec implements; the criterion is observed through the Playwright journeys named in requirement 11. "The last tasks" are this spec's tasks 10–13 and the UI spec's task 15, which run only if the owner says there is time; no other task depends on them, and a criterion that only they satisfy says so.

## Requirements

### Requirement 1

**User Story:** As an organizer comparing two scenarios, I want both of them run 30 times with the same simulated people and the same random draws, so that a difference in the numbers comes from the change I made and not from luck.

#### Acceptance Criteria

1. THE SYSTEM SHALL export from `src/comparison/paired.ts` the constants `REPLICATIONS = 30` and `REPLICATION_INDICES` equal to `[0, 1, …, 29]` (defined in `src/comparison/replications.ts`, which imports nothing, and re-exported, so `labels.ts` and `paired.ts` never import each other in a cycle), and `runPairedComparison(client, baseline, candidate, options)` in `src/comparison/runner.ts` SHALL request its runs only through the engine's `SimulationClient` passed in as `client`, never by creating a worker or calling `simulate` on the main thread.
2. WHEN `runPairedComparison` starts with two valid scenarios THEN it SHALL issue exactly four `client.run` calls in this order and one at a time: baseline with `REPLICATION_INDICES` and `trace: false`; candidate with `REPLICATION_INDICES` and `trace: false`; baseline with `[options.replayReplication]` and `trace: true`; candidate with `[options.replayReplication]` and `trace: true`, where `options.replayReplication` defaults to `0`.
3. WHEN the four runs complete THEN the runner SHALL resolve `{ status: 'complete', comparison }` where `comparison.baselineResults` and `comparison.candidateResults` each hold exactly 30 `RunResult`s sorted by `replication` 0–29, every `baseSeed` equals both scenarios' `baseSeed`, every `modelVersion` equals the engine's `MODEL_VERSION`, and every `scenarioHash` equals the hash of its own scenario.
4. IF `baseline.baseSeed !== candidate.baseSeed` THEN the runner SHALL resolve `{ status: 'error', code: 'SEED_MISMATCH', message: 'Baseline and candidate use different seeds ("<a>" and "<b>"); give both the same seed to compare them run for run.' }` before any run is requested; IF `baseline.horizonMs !== candidate.horizonMs` THEN it SHALL resolve `{ status: 'error', code: 'HORIZON_MISMATCH', message: 'Baseline and candidate use different observation windows (<a> min and <b> min); give both the same window to compare closing-time numbers.' }` before any run is requested.
5. IF either scenario fails `validateScenario` THEN the runner SHALL resolve `{ status: 'error', code: 'INVALID_SCENARIO', message }` with `message` equal to `Baseline: ` or `Candidate: ` followed by the first issue's message and ` (+<k> more)` when more issues exist, and SHALL request no run.
6. WHILE the runs are in progress THE SYSTEM SHALL call `options.onProgress(done, total)` with `total = 62` (30 + 30 + 1 + 1 replications) and `done` nondecreasing from 0 to 62, and the Compare screen SHALL show `Running paired replications: <done> of 62` (`data-testid="compare-status"`) and, on completion, `30 of 30 paired runs complete`.
7. WHEN `cancel()` is called on the handle returned by `runPairedComparison` THEN the runner SHALL call `client.cancel()` for the active run, request no further run, resolve `{ status: 'cancelled', message: 'Comparison cancelled.' }`, and SHALL leave any previously completed `Comparison` object held by the caller unchanged.
8. IF a run resolves with `status: 'error'` THEN the runner SHALL resolve `{ status: 'error', code: 'RUN_FAILED', message: 'Comparison failed: <worker message>' }` and request no further run; the previous comparison, if any, stays displayed with the UI's stale label.
9. WHEN the traced replay pair completes THEN for `r = options.replayReplication` the runner SHALL check `JSON.stringify(baselineReplay.metrics) === JSON.stringify(comparison.baselineResults[r].metrics)` and the same for the candidate; a mismatch SHALL resolve `{ status: 'error', code: 'NONDETERMINISTIC', message: 'Traced and untraced runs of replication <r> disagree; this is an engine defect and nothing was shown.' }`.
10. WHEN the runner completes THEN `comparison.timing` SHALL hold `{ pairedMs, replayMs }` measured with `performance.now()` around the two untraced runs and the two traced runs, shown by the Compare screen as `30 paired runs took <pairedMs / 1000 with one decimal> s on this device` and recorded as an observation, never as a performance claim.

### Requirement 2

**User Story:** As an organizer reading a comparison, I want the mean change, the spread across the 30 runs with a label that says what it is, and the number of runs in which the candidate did better, so that I never mistake simulated variation for a forecast or a prediction interval.

#### Acceptance Criteria

1. THE SYSTEM SHALL export `percentileIndex(p, n) = Math.max(0, Math.ceil(p * n) - 1)` from `src/comparison/percentiles.ts`, giving `percentileIndex(0.95, 20) = 18`, `percentileIndex(0.95, 1) = 0`, `percentileIndex(0.10, 30) = 2`, `percentileIndex(0.90, 30) = 26`, `percentileIndex(0.10, 1) = 0`, `percentileIndex(0.90, 1) = 0` (matrix row 26), and `percentileIndex(0.95, n)` SHALL equal the engine's `p95Index(n)` for every `n` from 1 to 5,000.
2. WHEN `pairResults(baselineResults, candidateResults, { baseline: baselineScenario.stations, candidate: candidateScenario.stations })` runs (the station lists supply the labels and the station ids of either side) THEN for every metric key of the design's metric table it SHALL produce a `PairedMetric` whose `differences[r] = candidate − baseline` for replication `r` (`null` when either side's `value` is `null`), with `n` equal to the count of non-null differences, `meanChange` the arithmetic mean of the non-null differences (`null` when `n = 0`), and `rangeP10` and `rangeP90` the ascending-sorted non-null differences at `percentileIndex(0.10, n)` and `percentileIndex(0.90, n)`.
3. THE SYSTEM SHALL label the range with exactly the string `variation across these simulated runs`, exported as `RANGE_LABEL` from `src/comparison/labels.ts` and carried on every `PairedMetric.rangeLabel`, every comparison CSV row and the printable comparison; the strings `confidence interval` and `prediction interval` SHALL not occur in `src/comparison/`, `src/exports/` or any output of this spec.
4. THE SYSTEM SHALL compute improvement counts only from `differences`: for `betterDirection: 'lower'`, `improved` = count of differences `< 0`, `worsened` = count `> 0`, `unchanged` = count `=== 0`; for `'higher'` the signs reverse; for `'none'` (`staffHours`, `stations.<id>.utilization`) the three counts SHALL be `null` and the rendered column shows `—`; `improved + worsened + unchanged === n` always; `tests/comparison/no-literal-counts.test.ts` SHALL fail if any file under `src/comparison/` or `src/exports/` contains a literal matching `/\b\d+\s*(of|\/)\s*30\s+runs\b/`, and every count sentence or completion text SHALL be composed at run time from the actual counts or from `REPLICATIONS` (template literals built from `REPLICATIONS`, such as `` `${REPLICATIONS} of ${REPLICATIONS} paired runs complete` ``, are the only permitted form of a fixed count).
5. WHEN the row-1 pair is compared (matrix row 23: constant service, even arrivals) THEN all 30 differences of `queueWait.mean` SHALL equal `-30000` ms, `meanChange` `-30000`, `rangeP10 === rangeP90 === -30000`, `improved === 30`, `n === 30` and the count text `30 of 30 runs`; `queueWait.p95` SHALL be `-60000`; `journeyTime.mean` `-30000`; `completedByClosing` `unchanged === 30`; `staffHours` `+0.05` h with null counts; the single station's `utilization` `-0.5`, `averageQueueLength` `-0.5` and `maxQueueLength` `-1`.
6. WHEN Harbor Hall `baseline` is compared with `plus-one-checkin` (matrix row 24) THEN `queueWait.mean` SHALL have `n === 30`, `meanChange` equal within `1e-9` to the mean the test recomputes from the 60 `RunResult`s, `improved` equal to the count the test recomputes, the rendered count text `<improved> of 30 runs`, and `RANGE_LABEL` SHALL appear in the metric card (`data-testid="metric-card-queueWait.mean"`, field `range`) and, once task 12 has run, in the printable comparison.
7. IF any replication of either scenario has `completion: 'drain-capped'` THEN every `PairedMetric` with population `completedJourney` SHALL carry `conditioned: true` and `note: '<k> of 30 baseline runs and <m> of 30 candidate runs hit the drain cap; completed-journey metrics count completed attendees only'`, and the rendered value SHALL carry the `*` suffix with the note shown beside the table.
8. THE SYSTEM SHALL format a difference with `formatChange(value, unit)`: `ms` as signed seconds with one decimal (`-30.0 s`), `count` and `people` as signed integers (`+3`), `ratio` as signed percentage points with one decimal (`-50.0 percentage points`), `hours` with two decimals (`+0.05 h`), `0` as the unit's zero followed by ` (no change)` (`0.0 s (no change)`), and `null` as `—`.
9. THE SYSTEM SHALL render the count sentence through one of two templates in `src/comparison/labels.ts` chosen by requirement 3: person-for-person `Candidate had <lower|higher> <metric> in <k> of <n> runs; the same simulated attendees and random draws were used in both.` or population `Candidate had <lower|higher> <metric> in <k> of <n> runs; the attendee populations differ (<a> vs <b> people), so this compares groups, not the same people.`; for `betterDirection: 'none'` the sentence is `No better direction is defined for <metric>; read the values.`

### Requirement 3

**User Story:** As an organizer who changed how many people come, I want the comparison to say loudly that the groups differ and to stop talking as if it were the same people, so that a shorter mean over a different crowd is never read as an improvement for everyone.

#### Acceptance Criteria

1. THE SYSTEM SHALL export `populationChange(baseline, candidate)` from `src/comparison/population.ts`, comparing the multiset of `(cohort.id, cohort.count)` pairs and returning `{ changed: false, baselineCount, candidateCount, details: [] }` when they are identical, otherwise `{ changed: true, baselineCount, candidateCount, details }` with one detail per difference in the forms `Cohort "doors": count 120 → 130 people`, `Cohort "gate" added (40 people)` and `Cohort "late" removed (12 people)`.
2. WHEN the candidate is Harbor Hall `baseline` with `doors.count` set to 130 (matrix row 25) THEN `changed` SHALL be `true` with `baselineCount 120` and `candidateCount 130`, and WHEN the candidate renames cohort `doors` to `gate` with the same count THEN `changed` SHALL also be `true`.
3. WHEN `changed` is `true` THEN `comparison.languageMode` SHALL be `'population'`, the change list SHALL begin with one entry of group `population` and `highlight: true` whose text is the joined `details`, every count sentence SHALL use the population template of 2.9, the Compare screen SHALL show the entry in `data-testid="population-change"`, and the string `the same simulated attendees` SHALL not occur in the comparison, the printable comparison or any CSV.
4. WHEN `changed` is `false` THEN `languageMode` SHALL be `'person-for-person'`, the count sentences SHALL use the person-for-person template and `data-testid="population-change"` SHALL be absent.
5. THE SYSTEM SHALL export `attendeePairs(selection, population)` returning `{ ok: false, code: 'POPULATION_CHANGED', message: 'Per-person comparison is off because the attendee populations differ.' }` when `changed` is `true`, and otherwise `{ ok: true, pairs }` with one entry per attendee ID `{ id, cohortId, arrivalMs, baselineWaitMs, candidateWaitMs, baselineJourneyMs, candidateJourneyMs }` built from the two traces of the selected replicate, where every ID present in one trace is present in the other.
6. WHEN Harbor Hall `baseline` and `plus-one-checkin` are paired for replication 0 THEN `attendeePairs` SHALL return 120 pairs with `arrivalMs` identical on both sides for every pair, and `baselineJourneyMs` and `candidateJourneyMs` SHALL both be `null` only for attendees listed in that scenario's `unfinished`.

### Requirement 4

**User Story:** As an organizer, I want a plain-language list of exactly what differs between two scenarios, in the units I typed, so that I can tell a judge or a colleague what the comparison is about.

#### Acceptance Criteria

1. THE SYSTEM SHALL export `diffScenarios(baseline, candidate)` from `src/comparison/diff.ts` returning `{ changes, kind, population }` where `changes` lists every differing value among `horizonMs`, `walkSpeedMps`, `baseSeed`, `layout.cols`, `layout.rows`, `layout.cellSizeM`, `layout.entrance`, `layout.exit`, `layout.blockedCells` (one entry: `Blocked cells: <k> added, <m> removed`), each station's `label`, `cell`, `servers` and `service`, each cohort's `startMs`/`endMs`, `count`, `arrivals` and `route`, and stations or cohorts added or removed; each entry carries `path` in the engine's path form, `group` (`population`, `staffing`, `service`, `layout`, `arrivals`, `timing`, `route`, `derived`), `label`, `before`, `after` and `highlight`.
2. THE SYSTEM SHALL render `before` and `after` in display units: windows as `0–20 min`, horizon as `40 min`, service as `triangular 8/15/22 s` or `constant 60 s`, walking speed as `1.2 m/s`, cell size as `0.5 m`, counts as `120 people`, cells as `(34,12)`, servers as the integer, routes as `checkin → packs`, with minutes shown with one decimal only when not whole.
3. THE SYSTEM SHALL never list `id`, `revision`, `title`, `notes`, `schemaVersion` or `modelVersion` as a change; differing titles appear only in the comparison header.
4. THE SYSTEM SHALL set `kind` to `'none'` for zero non-derived changes, `'single'` for one and `'combined'` for two or more, with the header text `No assumption differs between these scenarios.`, `1 change` or `<n> changes`, and for `'combined'` the additional line `Combined candidate: run each change on its own first to see which one moves the numbers.`
5. WHEN `baseline` is diffed against `plus-one-checkin` THEN `changes` SHALL contain exactly one non-derived entry `Station "Check-in desk": servers 1 → 2` with `kind: 'single'`; WHEN `baseline` is diffed against `shorter-route` THEN it SHALL contain exactly one non-derived entry `Station "Welcome packs": position (34,12) → (14,8)` plus the derived entry `Walking per attendee, cohort "doors": 38.0 m → 18.0 m (31.7 s → 15.0 s)` with `group: 'derived'`, and `kind` SHALL still be `'single'`.
6. THE SYSTEM SHALL compute derived walking entries from `createPathCache` of each scenario for every cohort route (entrance, stations in order, exit), SHALL order `changes` as population first, then staffing, service, layout, arrivals, timing, route and derived last, stable by `path` within a group, and SHALL render the list in the Compare screen as an ordered list under `data-testid="change-list"` with `data-kind` equal to `kind`.

### Requirement 5

**User Story:** As an organizer watching the replay, I want the baseline ghost and the candidate to show the same replicate on the same clock, with the ghost visibly different by more than colour, so that what I see is one honest example of the 30 runs.

#### Acceptance Criteria

1. THE SYSTEM SHALL export `selectReplay(comparison, r)` from `src/comparison/replay-contract.ts` returning `{ ok: true, selection: ReplaySelection { replication: r, baseline, candidate, label, clock } }` when traced results for `r` are loaded, otherwise `{ ok: false, code: 'TRACE_NOT_LOADED', message: 'Replication <r> has not been loaded for replay yet.' }`, where `baseline` and `candidate` are the traced `RunResult`s for replication `r`, `label` is `Replay of replication <r>, one example run`, and `clock` is `{ horizonMs, endMs }` with `endMs` the larger of the two traces' last event times, so both layers advance on one clock from 0.
2. IF `r` is not an integer from 0 to 29 THEN `selectReplay` SHALL return `{ ok: false, code: 'REPLICATION_RANGE', message: 'Replication must be between 0 and 29.' }`.
3. WHEN the organizer picks a replication in `data-testid="replicate-select"` THEN the runner's `selectReplicate(client, comparison, r)` SHALL request two traced runs (baseline `[r]`, then candidate `[r]`), the previous selection SHALL stay displayed with the status `Loading replication <r>…`, the new `ReplaySelection` SHALL replace it on completion, and `cancel()` SHALL behave as 1.7.
4. THE SYSTEM SHALL export `GHOST_STYLE = { role: 'baseline', alpha: 0.45, outline: 'dashed', fill: 'hatched', hue: 'orange' }`, `CANDIDATE_STYLE = { role: 'candidate', alpha: 1, outline: 'solid', fill: 'solid', hue: 'cyan' }` and `GHOST_LEGEND = 'Baseline: dashed outline, hatched, translucent · Candidate: solid'`; the game view SHALL draw from these constants and show `GHOST_LEGEND` under `data-testid="ghost-legend"`, the `label` under `data-testid="replay-label"`, and `data-replication="<r>"` on both `data-testid="replay-layer-baseline"` and `data-testid="replay-layer-candidate"`.
5. THE SYSTEM SHALL export `REPLAY_NOTE = 'This replay is one example run; the comparison numbers come from all 30.'` and the Compare screen SHALL show it next to the replay.
6. WHEN a `ReplaySelection` is produced THEN `selection.baseline.replication === selection.candidate.replication === r`, both `scenarioHash` values SHALL equal the comparison's, and each side's `metrics` SHALL `JSON.stringify`-equal the untraced result for `r` (1.9).

### Requirement 6

**User Story:** As an organizer, I want to save a scenario with its results as one file and load it again later or on another machine, so that the numbers reproduce and nothing is lost when browser storage is cleared.

#### Acceptance Criteria

1. THE SYSTEM SHALL export `exportScenarioJson({ scenario, scenarioHash, results, generatedAt })` from `src/exports/scenario-json.ts` returning UTF-8 JSON text with two-space indentation, LF line endings and a trailing newline, of `ScenarioExport { format: 'rehearsal-scenario', formatVersion: 1, generatedAt, modelVersion, baseSeed, scenarioHash, scenario, results, assumptions, limits }` where `scenario` is complete (including `id`, `revision`, `title`, `notes`), `results` is `[]` or one `{ replication, completion, unfinished, metrics }` per supplied `RunResult` sorted by `replication`, `assumptions` is `ASSUMPTIONS` and `limits` is `LIMITS_TEXT` from `src/exports/assumptions-text.ts`; the generator SHALL read no clock and no storage.
2. THE SYSTEM SHALL export `parseScenarioExport(text)`, the one parser behind every user-facing `.json` open or import, returning `{ ok: true, scenario, results, warnings }` or `{ ok: false, code, message, issues? }` with codes and messages: `FILE_TOO_LARGE` `This file is <n> MiB; the limit is 2 MiB.` (input over 2,097,152 bytes), `NOT_JSON` `This file is not valid JSON.`, `NOT_A_SCENARIO_EXPORT` `This file is not a Rehearsal scenario export (expected "format": "rehearsal-scenario") or a bare scenario (expected "schemaVersion": 1).`, `UNSUPPORTED_FORMAT_VERSION` `This export uses format version <v>; this build reads version 1.`, `SCENARIO_INVALID` with the first engine issue message plus ` (+<k> more)` and `issues` attached; unknown top-level keys SHALL be ignored. A bare `Scenario` object (no `format` key, top-level `schemaVersion: 1`, the shape of `public/examples/harbor-hall/baseline.json`) SHALL be accepted as `{ ok: true, scenario, results: [], warnings }` with only the engine's warnings, so the three supplied example files and a file saved by the editor before the envelope existed open through the same parser.
3. WHEN the recomputed `scenarioHash(scenario)` differs from the file's `scenarioHash` THEN `parseScenarioExport` SHALL still return the scenario with `results: []` and the warning `{ code: 'HASH_MISMATCH', message: 'The recorded scenario hash does not match the scenario in this file, so its saved results were discarded; the scenario itself was imported.' }`; WHEN the file's `modelVersion` differs from `MODEL_VERSION` THEN `results` SHALL be `[]` with the warning `{ code: 'RESULTS_MODEL_VERSION', message: 'Saved results came from model version <v>; this build is <MODEL_VERSION>, so they were discarded. Rerun to see results.' }` in addition to the engine's `MODEL_VERSION_MISMATCH` warning.
4. WHEN Harbor Hall `baseline` is exported with its 30 untraced results and parsed back (matrix row 27, re-import half) THEN the parsed scenario SHALL validate with no issues, its `scenarioHash` SHALL equal the exported one, and `simulate(scenario, 0, …)` and `simulate(scenario, 29, …)` SHALL produce `metrics` that `JSON.stringify`-equal `results[0].metrics` and `results[29].metrics`.
5. THE SYSTEM SHALL carry no playback speed, camera, zoom or other rendering setting in a `ScenarioExport`, so that a re-imported scenario reproduces regardless of how it was viewed (matrix row 10, export half).
6. WHEN the UI spec's `Open JSON` flow (`data-testid="import-json"` on the Plan screen, `Open a scenario JSON` on the landing screen; `scenario-editor-and-replay` 10.7, its task 19) receives a `.json` file THEN it SHALL call `parseScenarioExport`, show the preview with every warning of 6.3 verbatim, and apply atomically; on any `ok: false` the previous scenario and results SHALL be preserved and the message of 6.2 shown, observed in that task's `tests/imports/scenarioJson.test.ts` and the export and re-import steps of `tests/e2e/keyboard-journey.spec.ts`, and in `tests/e2e/exports.spec.ts` once the last tasks have run.

### Requirement 7

**User Story:** As an organizer who lives in spreadsheets, I want the assumptions and results as CSV and the assumptions as a workbook that I can edit and re-import, so that the tool fits my existing files and never plants a formula in them.

#### Acceptance Criteria

Availability: this requirement is delivered by the last tasks (this spec's tasks 10 and 11, the UI spec's task 15). Until they run, no screen offers a CSV or workbook export, and matrix row 27 is recorded for its re-import and HTML-escaping halves only (6.4, 8.2).

1. THE SYSTEM SHALL export `exportArrivalsCsv(scenario)` and `exportStationsCsv(scenario)` from `src/exports/csv.ts` producing exactly the template columns `cohort_id,start_min,end_min,count,arrival_pattern,route` and `station_id,label,servers,service_min_s,service_mode_s,service_max_s,cell_x,cell_y`, one row per cohort or station in scenario order, `start_min = startMs / 60000` and `end_min = endMs / 60000`, `route` joined with `|`, a constant service written as three equal values, through Papa Parse `unparse` with `escapeFormulae: true` and `newline: '\r\n'`.
2. THE SYSTEM SHALL export `exportResultsCsv(comparison)` with the columns `scenario,scenario_hash,model_version,base_seed,replication,completion,metric,unit,population,n,value`, one row per scenario (`baseline`, `candidate`), replication 0–29 and metric key (including `stations.<id>.<metric>`), `value` empty for `null`, so Harbor Hall `baseline` against `plus-one-checkin` yields `2 × 30 × (11 + 4 × 2)` rows.
3. THE SYSTEM SHALL export `exportComparisonCsv(comparison)` with the columns `metric,unit,population,baseline_mean,candidate_mean,mean_paired_change,p10,p90,range_label,n,runs_improved,runs_worsened,runs_unchanged,better_direction,conditioned,note`, `range_label` equal to `RANGE_LABEL` on every row and the three count columns empty when `betterDirection` is `'none'`.
4. WHEN a scenario has station label `=SUM(A1:A3)`, cohort id `+late`, title `-Harbor` and notes `@all` (matrix row 27, escaping half) THEN every CSV cell produced from those strings SHALL NOT begin with `=`, `+`, `-` or `@` (Papa Parse's `escapeFormulae` escape; the exact escape form is *verify* on the pinned 5.7.0), and a numeric `mean_paired_change` of `-30000` SHALL be passed as a number and parse back with `Papa.parse` to the number `-30000` (*verify* at task 1 that `escapeFormulae` leaves numeric values untouched; if it does not, log the observation and ask the owner before changing the column types).
5. THE SYSTEM SHALL export `exportWorkbook(scenario)` from `src/exports/xlsx.ts` returning the bytes of an xlsx workbook built with SheetJS Community Edition (Apache-2.0; 0.20.3 from the SheetJS CDN tarball, pinned by `scenario-editor-and-replay` task 2; the writer function names *verify* on that version at task 1) with exactly three sheets `Arrivals`, `Stations` and `Settings`, header rows equal to the template columns, `Settings` rows `title`, `horizon_min`, `walk_speed_mps`, `base_seed`, numbers written as numeric cells, text as text cells, and no formula cell anywhere.
6. WHEN the workbook for Harbor Hall `baseline` is read back with SheetJS THEN `Arrivals` SHALL equal `[['cohort_id','start_min','end_min','count','arrival_pattern','route'], ['doors', 0, 20, 120, 'uniform', 'checkin|packs']]`, `Stations` SHALL equal `[['station_id','label','servers','service_min_s','service_mode_s','service_max_s','cell_x','cell_y'], ['checkin','Check-in desk',1,8,15,22,10,12], ['packs','Welcome packs',2,6,10,14,34,12]]` and `Settings` SHALL equal `[['key','value'], ['title', <scenario.title>], ['horizon_min', 40], ['walk_speed_mps', 1.2], ['base_seed', 'harbor-hall-2026']]`.
7. WHEN the exported workbook is re-imported through the UI spec's xlsx adapter onto the same layout (package R7 acceptance) THEN the resulting canonical hash SHALL equal the exported scenario's hash, observed in `tests/e2e/exports.spec.ts` (the UI spec's task 15).

### Requirement 8

**User Story:** As an organizer, I want a printable comparison that states its seeds, model version and limits, and a one-page run sheet for the day of the event, so that what I hand to volunteers and committees carries its own assumptions.
