# Requirements Document

## Introduction

`simulation-contract` is the pure TypeScript engine of Rehearsal: it turns a validated `Scenario` into a `RunResult` with metrics and a replay trace, deterministically, off the main thread. It serves the organizer who compares staffing and layout choices (through the fleet-built editor, replay and comparison that consume its outputs) and the reviewer agent that checks its numbers by hand. It implements sections 5 (data model, units, limits, canonical hash, Harbor Hall fixture), 6 (simulation contract, spatial layout, worker protocol) and 7 (metrics) of `plans/rehearsal-implementation-plan.md` as spec 11.1 `simulation-contract`, owned by Kiro, implemented November 4–11 on branch `kiro/simulation-contract` under a 550-credit cap, feeding the November 11 gate and verification-matrix rows 1–12 plus the worker side of row 17. Code lives in `src/domain/`, `src/simulation/`, `src/spatial/` and `src/workers/`; tests in `tests/model/`; the regression snapshot in `public/examples/harbor-hall/expected.json`; the contract document in `docs/model-contract.md`.

Terms used below: `H` is `scenario.horizonMs`; "the cap" is `H + 7,200,000 ms`; "a settled instant" is the model state after every event at one timestamp has been applied and every station queue has been dispatched; "code-unit order" is the order of JavaScript's `<` on strings (UTF-16 code units, no locale); "the three Harbor Hall scenarios" are `baseline`, `plus-one-checkin` and `shorter-route` with the exact values in plan section 5; "the engine folders" are `src/domain/`, `src/simulation/` and `src/spatial/`.

## Requirements

### Requirement 1

**User Story:** As the simulation agent, I want one validated `Scenario` type with explicit units, numeric limits and a canonical hash, so that every module, import adapter and export works from the same object and two equal scenarios are provably the same input.

#### Acceptance Criteria

1. THE SYSTEM SHALL export from `src/domain/scenario.ts` the `Scenario` type with exactly the fields of plan section 5 (`schemaVersion: 1`, `id`, `revision`, `title`, `modelVersion`, `baseSeed`, `horizonMs`, `layout { cols, rows, cellSizeM, blockedCells, entrance, exit }`, `walkSpeedMps`, `stations[] { id, label, cell, servers, service }`, `cohorts[] { id, startMs, endMs, count, arrivals, route }`, `notes`) and a function `validateScenario(input: unknown)` that returns `{ ok: true, scenario, warnings }` or `{ ok: false, issues }`, where every issue carries `code`, `path`, `message` and, when it concerns a station or cohort, `entity: { kind, id }`.
2. THE SYSTEM SHALL keep internal time in integer milliseconds (`horizonMs`, `startMs`, `endMs`, every timestamp and duration in results) and service assumptions in seconds inside `Scenario`, converting seconds to milliseconds in exactly one function, `toDurationMs(seconds) = Math.max(1, Math.round(seconds * 1000))`, and SHALL reject any value whose millisecond form is not a safe integer.
3. IF a scenario violates a limit THEN `validateScenario` SHALL return `ok: false` with the matching code: total `count` over all cohorts above 5,000 (`ATTENDEE_LIMIT`); more than 10 stations (`STATION_LIMIT`); a route with more than 6 visits (`ROUTE_LENGTH`); `cols` or `rows` outside 1–80 (`GRID_SIZE`); `horizonMs` outside 1–21,600,000 (`HORIZON_RANGE`); `servers` not a whole number in 1–20 (`SERVERS_RANGE`); `count` not a whole number of 0 or more (`COUNT_RANGE`); `walkSpeedMps` or `cellSizeM` not a positive finite number (`WALK_SPEED`, `CELL_SIZE`); constant `seconds` not positive and finite, or triangular values not satisfying `0 < minS ≤ modeS ≤ maxS`, or any service value above 86,400 seconds (`SERVICE_RANGE`); a cohort window not satisfying `0 ≤ startMs < endMs ≤ horizonMs` (`COHORT_WINDOW`); `arrivals` not `even` or `uniform` (`ARRIVAL_PATTERN`); any non-finite number (`NON_FINITE`).
4. IF a scenario's identifiers or geometry are inconsistent THEN `validateScenario` SHALL return `ok: false` with: `DUPLICATE_ID` for a repeated station or cohort `id`; `ID_FORMAT` for an `id` that is empty, longer than 64 characters or contains `|` or `#`; `SEED_FORMAT` for a `baseSeed` that is empty, longer than 64 characters or contains `|`; `MODEL_VERSION_FORMAT` when `modelVersion` does not match `^\d+\.\d+\.\d+$`; `SCHEMA_VERSION` when `schemaVersion` is not `1`; `ROUTE_UNKNOWN_STATION` and `ROUTE_REPEAT` for a route naming an unknown station or the same station twice; `CELL_OUT_OF_BOUNDS` for an entrance, exit, station cell or blocked cell outside `0 ≤ x < cols`, `0 ≤ y < rows`; `CELL_BLOCKED` for an entrance, exit or station on a blocked cell; `DUPLICATE_BLOCKED_CELL` for a repeated blocked cell.
5. WHEN validation fails THEN THE SYSTEM SHALL return every issue found in one call (never only the first), each with `path` in the form `stations[2].servers`, `cohorts[0].route[1]`, `layout.blockedCells[4]` or `horizonMs`, and with the exact message text of the design's error table, and SHALL NOT mutate the input object.
6. THE SYSTEM SHALL compute `scenarioHash(scenario)` as the lowercase 64-character hexadecimal SHA-256 (Web Crypto `subtle.digest`) of `canonicalJson(scenario)`: the JSON of every field except `id`, `revision`, `title` and `notes`, with object keys sorted, `stations` and `cohorts` sorted by `id` in code-unit order, and `blockedCells` sorted by `x` then `y`; changing `title` or reordering `stations` SHALL leave the hash unchanged and changing any `servers` value SHALL change it.
7. WHEN `scenario.modelVersion` differs from the engine's `MODEL_VERSION` THEN validation SHALL still succeed and `warnings` SHALL contain `{ code: 'MODEL_VERSION_MISMATCH', message: 'This scenario was saved with model version <saved>; the engine is <engine>. Results may differ from the saved export.' }`.
8. IF any station or the exit cannot be reached from the entrance through unblocked four-neighbour moves, or any consecutive pair of a cohort's route (entrance, its stations in order, exit) cannot be joined THEN validation SHALL fail with `UNREACHABLE` and a message naming both endpoints, for example `No walkable path between station "checkin" (10,12) and station "packs" (14,8).`, and `simulate` SHALL never be entered with that scenario.

### Requirement 2

**User Story:** As an organizer comparing scenarios, I want every simulated attendee to keep the same identity and arrival time across candidate scenarios, so that a change in the result is caused by the change I made and not by renumbering.

#### Acceptance Criteria

1. THE SYSTEM SHALL give each attendee the ID `${cohortId}#${ordinal}` with the zero-based ordinal padded to four digits (`doors#0000` through `doors#0119` for a cohort of 120), derived only from the cohort and the ordinal, never from an array index after sorting.
2. WHEN a cohort's `arrivals` is `even` THEN the j-th attendee SHALL arrive at `startMs + Math.round((j + 0.5) * (endMs - startMs) / count)`, so that cohort `doors` (start 0, end 1,200,000 ms, count 120) arrives at `(j + 0.5) × 10,000` ms with the first at 5,000 ms and the last at 1,195,000 ms, all inside `[0, 1,200,000)` (matrix row 8).
3. IF rounding would place an even arrival at or beyond `endMs` THEN THE SYSTEM SHALL clamp it to `endMs - 1`, and SHALL never place one below `startMs` (count 1, start 0, end 1 → arrival 0).
4. WHEN a cohort's `arrivals` is `uniform` THEN each attendee SHALL take exactly one draw `u` from the generator keyed `${baseSeed}|${replication}|${attendeeId}|arrival` and arrive at `startMs + Math.floor(u * (endMs - startMs))`, which lies in `[startMs, endMs)`.
5. WHEN the attendee list is compiled THEN THE SYSTEM SHALL sort all attendees of all cohorts by `(arrivalMs, attendeeId)` in that order, keep their IDs unchanged by the sort, and every `arrivalMs` SHALL satisfy `startMs ≤ arrivalMs < endMs ≤ H`, so that every generated attendee is admitted.
6. THE SYSTEM SHALL accept overlapping arrival windows (two cohorts with `[0, 600,000)` and `[300,000, 900,000)` validate) and SHALL reject a repeated cohort `id` with `DUPLICATE_ID`.
7. WHEN a cohort has `count: 0` or a scenario has no cohorts THEN THE SYSTEM SHALL compile zero attendees for it without error (matrix row 11, population side).

### Requirement 3

**User Story:** As the simulation agent, I want every random draw to come from a local generator keyed by what the draw is for, so that corresponding attendees receive corresponding draws when a scenario changes and no hidden state leaks between runs.

#### Acceptance Criteria

1. THE SYSTEM SHALL draw a random service duration from a generator created by `createGenerator(key)` in `src/simulation/random.ts` with `key = ${baseSeed}|${replication}|${attendeeId}|${stationId}|service`, and an arrival draw with `key = ${baseSeed}|${replication}|${attendeeId}|arrival`; no key SHALL include the scenario `id`, `revision`, `title`, hash, any cell position, any `servers` value or any event-processing order.
2. THE SYSTEM SHALL NOT call, replace or reassign `Math.random`, and SHALL NOT read `Date.now`, `performance.now` or `new Date()` anywhere in the engine folders; `tests/model/purity.test.ts` SHALL scan every `.ts` file under those folders for the tokens `Math.random`, `Date.now`, `performance.now` and `new Date(` and fail on any occurrence.
3. WHEN `triangular(u, a, c, b)` is called THEN THE SYSTEM SHALL return `a + Math.sqrt(u * (b - a) * (c - a))` when `u ≤ (c - a) / (b - a)` and `b - Math.sqrt((1 - u) * (b - a) * (b - c))` otherwise, so that `(10, 20, 30)` with `u = 0.125, 0.5, 0.875` returns `15, 20, 25` seconds before millisecond conversion (matrix row 5).
4. WHEN a station's service is `{ kind: 'constant', seconds }` or a triangular service has `minS === maxS` THEN THE SYSTEM SHALL use the constant duration and SHALL NOT create a generator or take a draw for that visit.
5. THE SYSTEM SHALL convert every sampled or constant duration with `toDurationMs`, so that a sampled 0.0004 s becomes 1 ms and no service duration is ever 0 ms.
6. WHEN the three Harbor Hall scenarios are compiled for the same `baseSeed` and replication (0 and 7 are tested) THEN every attendee's `arrivalMs` and every visit's sampled `serviceMs` SHALL be identical across `baseline`, `plus-one-checkin` (check-in `servers` 2) and `shorter-route` (`packs` moved to (14,8)) (matrix row 9).
7. WHEN `createGenerator('rehearsal|0|doors#0000|checkin|service')` is created twice THEN the two generators SHALL produce the same first ten values, and those values SHALL lie in `[0, 1)`.

### Requirement 4

**User Story:** As the simulation agent, I want one event scheduler with a fixed ordering rule for equal-time events, so that an arriving attendee can never take a server ahead of someone already waiting and every run is reproducible.

#### Acceptance Criteria

1. THE SYSTEM SHALL schedule events in a binary min-heap (`src/simulation/heap.ts`) ordered by `(timeMs, kindPriority, attendeeId, sequence)` with `kindPriority` service completion = 0, movement arrival = 1, external arrival = 2, `attendeeId` compared in code-unit order and `sequence` a per-run counter incremented on every push; pushing 1,000 events in shuffled order SHALL pop them in exactly that order, `size()` SHALL track pushes and pops, and `pop()` on an empty heap SHALL return `undefined`.
2. WHEN the next event has timestamp `t` THEN THE SYSTEM SHALL pop and apply every event with `timeMs === t`, including movement arrivals pushed at `t` while the batch runs (zero-length transfers), before dispatching any queue; THEN it SHALL visit stations in code-unit order of `station.id` and dispatch each line.
3. WHEN a station is dispatched THEN THE SYSTEM SHALL serve its line in `(queueJoinMs, attendeeId)` order, assign each served attendee the lowest-numbered free server (0-based `server` index), set `serviceStartMs = t`, and push a service completion at `t + serviceMs` with `serviceMs ≥ 1`, so no dispatch ever creates an event at `t`.
4. WHEN a service completion is applied THEN THE SYSTEM SHALL release exactly one server (the one named in the event) and send the attendee walking to the next station of its route or to the exit, with the duration from the path cache; a zero duration SHALL push a movement arrival at the same `t` that is applied in the same batch.
5. WHEN matrix row 1 runs (one server; arrivals 0, 30,000 and 60,000 ms; constant 60 s service; one cell for entrance, station and exit so walking is 0; `H` = 180,000 ms) THEN service starts SHALL be 0, 60,000, 120,000; exits 60,000, 120,000, 180,000; waits 0, 30,000, 60,000 ms; mean wait 30,000 ms; p95 wait 60,000 ms; utilization 1.0; average queue length 0.5; maximum settled queue length 1; completed by closing 3.
6. WHEN matrix row 2 runs (row 1 with two servers) THEN starts SHALL be 0, 30,000, 60,000; exits 60,000, 90,000, 120,000; every wait 0; utilization 0.5 over 180,000 ms; completed by closing 3.
7. WHEN matrix row 3 runs (attendees `a#0000` and `a#0001` arriving at 0 and `c#0000` at 10,000 ms; one server; constant 10 s service; zero walking) THEN the service order SHALL be `a#0000`, `a#0001`, `c#0000` with starts 0, 10,000, 20,000 ms: at `t = 10,000` the completion (priority 0) and the external arrival (priority 2) are both applied before dispatch, and the line order `(queueJoinMs, attendeeId)` places `a#0001` (joined at 0) ahead of `c#0000` (joined at 10,000).
8. THE SYSTEM SHALL keep the per-station line sorted by `(queueJoinMs, attendeeId)` on insertion, so the final line order at a settled instant does not depend on the order in which same-timestamp arrivals were applied.
9. THE SYSTEM SHALL expose the scheduler as `runSchedule(input: ScheduleInput): ScheduleOutput` over already-resolved inputs (attendees with `arrivalMs` and routes, stations with `servers` and a `serviceMs(attendeeId)` function, a travel table), so that rows 1–3 run without the arrival, sampling or grid modules.

### Requirement 5

**User Story:** As an organizer moving a station on the floor plan, I want walking distances and durations computed from the grid, so that a moved station changes the model's numbers and not only the picture.

#### Acceptance Criteria

1. THE SYSTEM SHALL treat a cell as `[x, y]` with `x` growing east and `y` growing south, and SHALL find paths by breadth-first search through unblocked in-bounds cells with a FIFO queue, enqueuing the four neighbours in the fixed order north `(x, y-1)`, east `(x+1, y)`, south `(x, y+1)`, west `(x-1, y)`, recording each cell's parent on first discovery, and returning the parent chain from goal to start.
2. THE SYSTEM SHALL compute `distanceM = edgeCount * cellSizeM` and `durationMs = Math.ceil(distanceM / walkSpeedMps * 1000)`, with `0` edges, `0` m and `0` ms when start and goal are the same cell.
3. WHEN matrix row 4 runs (3 × 3 grid, `cellSizeM` 0.5, start (0,1), goal (2,1), `walkSpeedMps` 1) THEN the direct path SHALL have 2 edges, 1 m and 1,000 ms; WHEN (1,1) is blocked THEN the path SHALL be exactly `[(0,1), (0,0), (1,0), (2,0), (2,1)]` with 4 edges, 2 m and 2,000 ms, and computing it twice SHALL return equal arrays (north tie-break, stable across runs).
4. WHEN the Harbor Hall layout is evaluated (40 × 24 cells, `cellSizeM` 0.5, stage blocked at `x` 16–23 and `y` 20–23, entrance (0,12), exit (0,4), `walkSpeedMps` 1.2) THEN the baseline segments SHALL be entrance → `checkin` (10,12): 5 m, 4,167 ms; `checkin` → `packs` (34,12): 12 m, 10,000 ms; `packs` → exit: 21 m, 17,500 ms; 38 m per attendee; and the shorter-route segments with `packs` at (14,8) SHALL be 5 m, 4,167 ms; 4 m, 3,334 ms; 9 m, 7,500 ms; 18 m per attendee.
5. THE SYSTEM SHALL compute every path between the entrance, each station and the exit at most once per layout through `createPathCache({ layout, stations, walkSpeedMps })`, whose `key` is the canonical JSON string of `layout`, the stations' `(id, cell)` pairs sorted by `id` and `walkSpeedMps`; moving `packs` from (34,12) to (14,8) SHALL produce a cache with a different `key` and a different `checkin → packs` duration.
6. IF two nodes are not connected THEN `findPath` SHALL return `null` and the path cache SHALL report `{ ok: false, from, to }` so that validation emits the `UNREACHABLE` message of 1.8 naming both endpoints.
7. WHEN an attendee departs a node at `departMs` THEN its movement arrival SHALL be scheduled at exactly `departMs + durationMs` from the path cache, observable in the trace as `segment.endMs - segment.startMs === path.durationMs`.
8. THE SYSTEM SHALL list every path used by a run in `Trace.paths` with its cells, so the replay draws the walk the model timed and never a path of its own.

### Requirement 6

**User Story:** As an organizer reading closing-time numbers, I want the model to stop admitting people at the horizon, finish the people already inside, and tell me when it could not finish everyone, so that no statistic quietly excludes the people still waiting.

#### Acceptance Criteria

1. THE SYSTEM SHALL admit only external arrivals with `arrivalMs < H`; validation guarantees every generated arrival satisfies this, and the engine SHALL count the admitted attendees as `admitted`.
2. WHEN a service completion or exit falls at exactly `H` THEN THE SYSTEM SHALL process it and count the attendee as completed by closing (row 1: the exit at 180,000 ms with `H` = 180,000 counts).
3. WHEN all events at or before `H` are processed THEN THE SYSTEM SHALL continue applying events until the heap is empty or the next event's `timeMs` exceeds `H + DRAIN_CAP_MS` with `DRAIN_CAP_MS = 7,200,000`; an event with `timeMs` ≤ the cap is applied, a later one is not.
4. WHEN matrix row 6 runs (one server; one arrival at 0; constant 100 s service; zero walking; `H` = 60,000 ms) THEN busy time SHALL be clipped to 60,000 ms with utilization 1.0, completed by closing 0, still active at closing 1 (in service 1, walking 0, waiting 0), and journey statistics SHALL have `n = 1` with exit 100,000 ms and `completion: 'complete'`.
5. WHEN matrix row 7 runs (cohort `late`, count 2, even arrivals in `[0, 60,000)` giving 15,000 and 45,000 ms; one server; constant 4,000 s service; zero walking; `H` = 60,000 ms) THEN `completion` SHALL be `'drain-capped'`, `unfinished` SHALL equal `['late#0001']`, every metric over the completed-journey population SHALL carry `conditioned: true` with `n = 1`, and the trace SHALL end with a `cap` event at 7,260,000 ms.
6. WHEN `completion` is `'drain-capped'` THEN every metric whose `population` is `completedJourney` SHALL carry `conditioned: true` and `note: 'from <n> of <admitted> admitted attendees; <k> unfinished at the drain cap'`, and no completion-conditioned value SHALL be presented without it.
7. WHEN every admitted attendee exits at or before the cap THEN `completion` SHALL be `'complete'`, `unfinished` SHALL be `[]` and no metric SHALL carry `conditioned: true`.

### Requirement 7

**User Story:** As an organizer, I want every number to come with its unit, its population and its denominator, and an honest dash when it is undefined, so that I can explain a result and never read a fabricated zero.

#### Acceptance Criteria

1. THE SYSTEM SHALL compute in `src/simulation/metrics.ts` exactly the ten metrics of plan section 7: completed by closing (exit ≤ `H`); still active at closing (arrived before `H`, not exited by `H`, split walking / waiting / in service); total queue wait (sum of `serviceStartMs - queueJoinMs` over an attendee's visits, excluding walking and service); mean and p95 queue wait; total journey time (exit minus external arrival, when complete); mean walking time (sum of route walking durations per admitted attendee); station utilization (busy-server milliseconds clipped to `[0, H]` divided by `servers * H`); average queue length (time integral of the settled waiting count over `[0, H]` divided by `H`); maximum queue length (maximum waiting count at settled instants); staff-hours (`sum(servers) * H / 3,600,000`).
2. THE SYSTEM SHALL return every metric as `MetricValue { value: number | null, unit, population, n, conditioned, note }` with `unit` one of `count`, `ms`, `ratio`, `people`, `hours`, `population` one of `admitted`, `completedJourney`, `closingWindow`, and `n` the size of that population.
3. WHEN a p95 is computed over `n` values THEN THE SYSTEM SHALL return the ascending-sorted element at index `Math.ceil(0.95 * n) - 1`: index 18 for `n = 20`, index 0 for `n = 1`, index 2 for `n = 3` (row 1's p95 wait of 60,000 ms).
4. WHEN a scenario has zero cohorts or only cohorts with `count: 0` THEN counts SHALL be 0, `queueWait.mean`, `queueWait.p95`, `queueWait.total`, `journeyTime.mean`, `journeyTime.p95` and `walkingTime.mean` SHALL have `value: null` with `n: 0`, `formatMetricValue` SHALL render each as `—` (U+2014), and station utilization, average queue length and maximum queue length SHALL be `0` with staff-hours still defined (matrix row 11).
5. THE SYSTEM SHALL never emit `NaN`, `Infinity`, the strings `NaN`, `null` or `undefined`, or a fabricated `0` for an undefined average or percentile; `formatMetricValue` SHALL render `null` as `—`, `count` and `people` as whole numbers, `ms` as seconds with one decimal and the suffix ` s`, `ratio` as a percentage with one decimal and `%`, and `hours` with two decimals and ` h`.
6. WHEN utilization is computed THEN each busy interval `[serviceStartMs, completionMs)` SHALL be clipped to `[0, H]` before summing, so row 1 gives 1.0, row 2 gives 0.5 and row 6 gives 1.0.
7. WHEN average and maximum queue length are computed THEN THE SYSTEM SHALL integrate the waiting count only between settled instants and only over `[0, H]`, giving 0.5 and 1 for row 1 and 0 and 0 for row 2.
8. WHEN staff-hours are computed for Harbor Hall THEN `baseline` SHALL give `(1 + 2) * 2,400,000 / 3,600,000 = 2` hours and `plus-one-checkin` SHALL give `4 * 2,400,000 / 3,600,000` hours, rendered `2.00 h` and `2.67 h`.
9. WHEN mean walking time is computed for Harbor Hall THEN every `baseline` attendee SHALL contribute `4,167 + 10,000 + 17,500 = 31,667` ms and every `shorter-route` attendee `4,167 + 3,334 + 7,500 = 15,001` ms, over the `admitted` population.
10. THE SYSTEM SHALL return per-station metrics (`servers`, `busyMs`, `utilization`, `averageQueueLength`, `maxQueueLength`, `served`) in code-unit order of station `id`, plus overall `queues.averageLength` and `queues.maxLength` over the sum of all waiting counts, and the still-active split SHALL satisfy `walking + waiting + inService = total`.

### Requirement 8

**User Story:** As the fleet agent writing the game view, I want a compact trace that the replay can draw at any speed without touching model state, so that playback speed, scrubbing and the follow camera can never change a number.

#### Acceptance Criteria

1. WHEN `simulate` is called with `options.trace === true` THEN THE SYSTEM SHALL return `trace` with `version: 1`, `paths[]` (id, from, to, cells, `distanceM`, `durationMs`), `attendees[]` (id, `cohortId`, `arrivalMs`, `exitMs | null`), `events[]` in processing order and `segments[]`; WHEN `options.trace` is `false` THEN `trace` SHALL be `undefined` and `metrics` SHALL be byte-identical to the traced run's `metrics`.
2. THE SYSTEM SHALL emit one `MovementSegment { attendeeId, startMs, endMs, pathId }` per walk, with `endMs - startMs` equal to the referenced path's `durationMs`, and SHALL store no per-millisecond positions.
3. THE SYSTEM SHALL emit events of exactly the kinds `arrive`, `depart`, `join`, `start`, `complete`, `exit` and `cap`, and for every attendee the sequence SHALL read `arrive`, then for each visit `depart`, `join`, `start`, `complete`, then `depart`, `exit` (or stop early when unfinished), with timestamps nondecreasing along that sequence.
4. THE SYSTEM SHALL bound the trace by the input: at most `3 + 4 * visits` events and `visits + 1` segments per attendee, so a 5,000-attendee, 6-visit scenario has at most 135,000 events and 35,000 segments.
5. WHEN the same scenario, `baseSeed` and replication are simulated twice, and once more after `JSON.parse(JSON.stringify(scenario))` THEN `JSON.stringify(result)` SHALL be identical for all three runs (matrix row 10, engine half; the playback-speed and follow-camera half is row 10 in `scenario-editor-and-replay`).
6. THE SYSTEM SHALL give `simulate` no playback, speed, camera or rendering parameter, and `tests/model/purity.test.ts` SHALL fail if any file in the engine folders or `src/workers/` imports from `pixi.js`, `react`, `react-dom`, `src/replay`, `src/ui`, `src/imports`, `src/storage`, `src/comparison` or `src/exports`.
7. WHEN the queue inspector needs the line at time `t` THEN the trace SHALL be sufficient to reconstruct it: each `join` event carries `stationId` and `position`, the entry's 0-based index in the line after every event at `t` has been applied and before any dispatch at `t` (row 1 at `t` = 60,000: `c#0000` joins with `position: 1` behind `b#0000`, then `b#0000` is dispatched), and each `start` carries `server` (0-based) and `waitMs`.

### Requirement 9

**User Story:** As an organizer who pressed Simulate, I want progress, a cancel that always works and no stale numbers, so that a long run never freezes the page or shows results from a request I abandoned.

#### Acceptance Criteria

1. THE SYSTEM SHALL implement in `src/workers/` the message types `ToWorker` (`run { runId, scenario, replications, trace }`, `cancel { runId }`) and `FromWorker` (`progress { runId, done, total }`, `result { runId, replication, result }`, `cancelled { runId }`, `error { runId, message }`) exactly as plan section 6, and SHALL validate every incoming message on both sides with a zod schema before acting on it.
2. THE SYSTEM SHALL give every `run` a `runId` greater than every earlier one from the same adapter (starting at 1), SHALL increment the adapter's current `runId` on every `cancel()` and every new `run()`, and SHALL discard, without delivering to any callback, any `progress`, `result` or `error` whose `runId` is not the current one and any `cancelled` whose `runId` matches no pending cancel, counting each in `discardedMessages`; the one exception is an `error` with `runId` 0, which resolves the current run as `{ status: 'error', message: 'Malformed worker message.' }` (9.9).
3. WHEN the worker finishes a replication THEN it SHALL post `result` for it immediately and SHALL post `progress` only when at least 200 ms of worker time have passed since the previous `progress` of that run, so that progress is posted at most 5 times per second.
4. WHEN `cancel()` is called THEN the adapter SHALL post `cancel { runId }`, and IF `cancelled { runId }` does not arrive within 250 ms THEN the adapter SHALL call `terminate()` on the worker, create a new worker, resolve the run as `{ status: 'cancelled' }` and report `Simulation cancelled. The simulation worker did not respond within 250 ms and was restarted.`; IF `cancelled` arrives in time THEN the run resolves `{ status: 'cancelled' }` with the message `Simulation cancelled.`
5. WHEN the worker receives `cancel` for its active run THEN it SHALL stop before starting the next replication, post `cancelled { runId }` and post no further `result` or `progress` for that `runId`; the worker SHALL yield to its event loop between replications so a `cancel` can be observed.
6. WHEN a `result` for an older `runId` is delivered after a newer run started (matrix row 17, worker side) THEN the adapter SHALL discard it, `onResult` SHALL NOT be called for it, and the newer run's results SHALL be unaffected.
7. IF the scenario in a `run` message fails `validateScenario` or `simulate` throws THEN the worker SHALL post `error { runId, message }` with the first issue's message (followed by ` (+<k> more)` when more issues exist) or the thrown error's message, SHALL NOT terminate, and SHALL serve the next `run` normally.
8. WHEN a `run` message is processed THEN the worker SHALL compute `scenarioHash` once and stamp the same value, `MODEL_VERSION`, `baseSeed`, `replication`, `horizonMs`, `completion`, `unfinished`, `metrics` and (when requested) `trace` into every `RunResult` of that run.
9. IF an incoming message fails schema validation THEN the receiver SHALL ignore it except that the worker posts `error { runId: 0, message: 'Malformed worker message.' }` when the message has no numeric `runId`, and the adapter resolves the current run, if one is pending, as `{ status: 'error', message: 'Malformed worker message.' }` on an `error` with `runId` 0 (the exception named in 9.2).
10. THE SYSTEM SHALL create the worker from a Vite-resolvable module worker URL (`new Worker(new URL('./simulation.worker.ts', import.meta.url), { type: 'module' })`, *verify* on the pinned Vite) and SHALL run `simulate` only inside the worker, never on the main thread.
11. IF the worker fires `onerror` (an uncaught exception at its top level, or the browser stopping it) or `onmessageerror` (a message that could not be delivered, for example a structured-clone failure on a 135,000-event trace) THEN the adapter SHALL resolve the current run, if one is pending, as `{ status: 'error', message: 'The simulation worker stopped unexpectedly: <event message, or "message could not be delivered" for onmessageerror>.' }`, SHALL call `terminate()` on the worker and create a new one, SHALL increment `currentRunId`, and SHALL serve the next `run()` on the new worker; `WorkerLike` SHALL expose `onerror` and `onmessageerror` so that `tests/model/worker.test.ts` can fire both through the fake worker.
12. WHEN `run(scenario, [])` is called THEN the adapter SHALL resolve `{ status: 'complete', results: [] }` without posting any message and without changing `currentRunId`.

### Requirement 10

**User Story:** As the reviewer agent, I want machine-checked invariants over generated scenarios with reproducible failures, so that a scheduler bug no hand fixture covers is found and can be replayed from a saved seed.

#### Acceptance Criteria

1. THE SYSTEM SHALL hold in `tests/model/properties.test.ts` a fast-check suite over generated valid scenarios (grids 2 × 2 to 8 × 8 with random blocked cells that keep every node reachable, 0–3 stations, 0–3 cohorts, 0–40 attendees in total, `H` 60,000–600,000 ms, constant or triangular service 1–120 s, `walkSpeedMps` 0.5–2, both arrival patterns) with 200 runs per property.
2. THE SYSTEM SHALL check conservation: at every settled instant reconstructed from the trace, `admitted = walking + waiting + inService + exited`, where `admitted` counts attendees whose `arrive` event has been applied.
3. THE SYSTEM SHALL check nonnegative waits (`serviceStartMs ≥ queueJoinMs` for every `start`), no overlapping jobs on one server (for each station and server index the intervals `[startMs, completeMs)` are pairwise disjoint), ordered times within a visit (`join ≤ start < complete ≤ next depart`), and valid routing (each attendee's `join` events name exactly its cohort's route stations in order and an `exit` follows the last `complete` unless the attendee is listed in `unfinished`).
4. THE SYSTEM SHALL check serialization equivalence (`simulate(JSON.parse(JSON.stringify(s)))` equals `simulate(s)` byte for byte) and determinism (two runs of the same inputs are byte-identical; and, for a generated scenario with at least one attendee in a `uniform` cohort or at least one visit to a triangular station with `minS < maxS`, the raw draws of replications 0 and 1 differ for at least one such attendee or visit: `createGenerator(arrivalKey(baseSeed, 0, id))()` versus `createGenerator(arrivalKey(baseSeed, 1, id))()`, and `createGenerator(serviceKey(baseSeed, 0, id, stationId))()` versus the replication-1 key; scenarios with no such attendee or visit are excluded from that clause, and the generator of 10.1 gives every `uniform` cohort a window of at least 1,000 ms and every triangular service `minS < maxS`).
5. THE SYSTEM SHALL check common random inputs: changing one station's `servers` within 1–20 or moving one station to another reachable cell leaves every attendee's `arrivalMs` and every visit's `serviceMs` unchanged.
6. THE SYSTEM SHALL check FIFO dispatch (within one station, `start` events occur in `(queueJoinMs, attendeeId)` order), horizon bounds (no `arrive` event at or after `H`, no event after the cap, `unfinished.length > 0` if and only if `completion === 'drain-capped'`) and metric bounds (`0 ≤ utilization ≤ 1`, `busyMs ≤ servers * H`, `0 ≤ averageQueueLength ≤ maxQueueLength`).
7. THE SYSTEM SHALL check path properties: without blocked cells the path length equals the Manhattan distance; every path's consecutive cells are four-adjacent, in bounds and unblocked; `length(a → b) = length(b → a)`; and the canonical hash is unchanged by permuting `stations`, `cohorts` or `blockedCells` and by changing `id`, `revision`, `title` or `notes`.
8. IF a property fails THEN THE SYSTEM SHALL append `{ property, seed, path, counterexample, date }` to `tests/model/failing-seeds.json` (committed), rethrow the failure, and replay every saved seed first on the next run; the property SHALL NOT be weakened to pass and the entry SHALL stay until the fix is logged in `docs/kiro-log.md`.
9. THE SYSTEM SHALL NOT contain any assertion that adding servers improves every metric, or any metric, for every scenario.
10. WHEN `npm run test:model` runs on the builder's named laptop THEN the whole `tests/model` suite SHALL finish within 60 s (target; the measured time is recorded in the log, not claimed elsewhere).
