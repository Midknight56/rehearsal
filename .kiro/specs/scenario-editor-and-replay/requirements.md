# Requirements Document

## Introduction

`scenario-editor-and-replay` is the visible product of Rehearsal: the Plan screen (arrivals and stations tables, the grid floor plan with drag, coordinate form, keyboard nudge and obstacle editing, undo/redo, the assumptions panel), the CSV and `.xlsx` import adapters with preview and atomic apply, the run controls on the UI side of the engine's worker adapter, the PixiJS **Game view** with its follow-this-attendee camera, person timeline and queue inspector, the Compare screen with the synchronized baseline ghost and the replicate selector over the `src/comparison/` contract, the Print screen that renders the one-page run sheet, the landing screen, the bounded saved-scenario store, the Playwright journeys (including the four that `paired-comparison-and-release` specifies) and the storyboard capture scripts under `tests/video/`. It serves the organizer of a small community event who edits assumptions in a spreadsheet, watches the replay, compares two scenarios and prints a run sheet, and the judge who opens the hosted demo. It implements sections 5 (templates, xlsx rules, table–map agreement, limits), 8 (interface, accessibility), 9 (rendering budget, privacy, resilience), 14 (storyboard capture) and the `scenario-editor-and-replay` entry of section 11.1 of `plans/rehearsal-implementation-plan.md` (revision 2, 2026-11-03), as changed by `.kiro/steering/revision-2026-11-16.md`, on top of the contracts `simulation-contract` has landed in `src/domain/`, `src/spatial/`, `src/simulation/` and `src/workers/` and the contracts `paired-comparison-and-release` lands in `src/comparison/` and `src/exports/`, all consumed by name and never redefined here. Kiro does every task of this spec, including edits to this spec's own files; there is no fleet, integrator, worktree or reviewer agent. Order (revision steering): tasks 1–14, 16 and 17 run before `paired-comparison-and-release` and use nothing from `src/comparison/` or `src/exports/`; the parts that need those modules (Requirement 12, 10.5, 10.7, the JSON and save steps of 9.3) are tasks 18 and 19, run after that spec's task 9; Requirement 8 except the replay half of 8.5, 2.8 and the export controls of 12.2 that need that spec's tasks 10–13 are task 15, run last and only if the owner says there is time; Requirement 13 is task 20, after deployment. If task 15 does not run, the round trip ends at the replay and no screen offers a print, run-sheet or workbook-export control. Matrix rows 13–22 of the plan belong to this spec, together with the UI halves of rows 24, 25, 27 and 28 and the journeys of the comparison spec's Requirement 11.5; the import → simulation → replay round trip of 8.5 on one scenario is its acceptance (with the print half when task 15 runs).

Terms used below. **Scenario**: the `Scenario` record (`schemaVersion: 1`) of `src/domain/scenario.ts`, the only editing state; **canonical hash**: SHA-256 of the canonical JSON of every field except `id`, `revision`, `title` and `notes`, computed by `scenarioHash` of `src/domain/hash.ts`; **committed edit**: one reducer action that changes the scenario and creates one undo entry; **results**: the `RunResult` of the last completed run of one tab together with the scenario snapshot it was computed from; **stale**: results whose snapshot hash differs from that tab's current canonical hash; **trace**: `RunResult.trace`, the `Trace` of `src/simulation/trace.ts` (events `arrive`, `depart`, `join`, `start`, `complete`, `exit`, `cap`; segments with `pathId`; the `paths[]` table); **clock**: the replay's simulated time in integer milliseconds, display state only; **client**: the engine's `SimulationClient` of `src/workers/client.ts` (`run`, `cancel`, `dispose`, `currentRunId`), which owns `runId` numbering, cancellation and the discard of late messages; **comparison**: the `Comparison` record of `src/comparison/comparison.ts` produced by `runPairedComparison`; **wrapper**: the focusable `role="application"` element of the floor plan or of the game view; **status region**: the one `role="status"` element of the app; **named laptop**: the machine and browser the builder names in `docs/performance.md`; **test build**: a build made with the e2e flag that exposes `window.__rehearsal` (10.8); **tab key**: the stable key of an open tab, the example file's stem (`baseline`, `plus-one-checkin`, `shorter-route`) for the three Harbor Hall tabs and the scenario `id` for every other tab, used in `data-testid` values such as `scenario-tab-<tab key>` and `pick-baseline-<tab key>`; **Harbor Hall**: the fixture of the plan's section 5 (`public/examples/harbor-hall/`, the three JSON files written by `simulation-contract` task 15 with ids `harbor-hall-baseline`, `harbor-hall-plus-one-checkin`, `harbor-hall-shorter-route` and titles `Harbor Hall Community Fair: baseline`, `Harbor Hall Community Fair: extra check-in staff`, `Harbor Hall Community Fair: shorter walking route`), baseline grid 40 × 24, `cellSizeM` 0.5, stage blocked at x 16–23 and y 20–23, entrance (0,12), exit (0,4), cohort `doors` (120 attendees, 0–20 min, `uniform`, route `checkin|packs`), stations `checkin` "Check-in desk" at (10,12) with 1 server and triangular 8/15/22 s and `packs` "Welcome packs" at (34,12) with 2 servers and triangular 6/10/14 s, horizon 40 min, seed `harbor-hall-2026`, `modelVersion` `0.1.0`.

## Requirements

### Requirement 1 — CSV templates and import with preview and atomic apply

**User Story:** As an organizer, I want to download the two CSV templates, fill them in my spreadsheet application and import them through a preview that names every problem by row and field, so that my assumptions enter the model exactly as typed and never half-way.

#### Acceptance Criteria

1. WHEN `Download templates` is activated on the Plan screen THEN THE SYSTEM SHALL offer `arrivals.csv`, `stations.csv` and `rehearsal-template.xlsx` as downloads served byte-for-byte from `public/examples/` (no runtime generation), where `arrivals.csv` is the header `cohort_id,start_min,end_min,count,arrival_pattern,route` plus the row `doors,0,20,120,uniform,checkin|packs` and `stations.csv` is the header `station_id,label,servers,service_min_s,service_mode_s,service_max_s,cell_x,cell_y` plus the rows `checkin,Check-in desk,1,8,15,22,10,12` and `packs,Welcome packs,2,6,10,14,34,12`.
2. WHEN one or both files are chosen in the import dialog (`Arrivals CSV` = `data-testid="import-arrivals-csv"`, `Stations CSV` = `import-stations-csv`; either alone is allowed) THEN THE SYSTEM SHALL parse each with Papa Parse (MIT, 5.7.0 per plan section 4) with `dynamicTyping: false` into rows of strings, treat row 1 as the header, match header names exactly and in any order, list columns outside the template in the preview as `Columns not read: <names>` without reading them into the scenario, skip rows whose cells are all blank, and show the preview (parsed rows in display units, the error list, `Apply import`) within 1,000 ms for a 2 MiB file on the named laptop (a target until recorded).
3. IF a chosen file is larger than 2,097,152 bytes THEN THE SYSTEM SHALL refuse it before parsing with `<file name> is <size> MiB; the limit is 2 MiB.` (size with two decimals), keep the dialog open and build no preview.
4. THE SYSTEM SHALL parse every numeric field explicitly from its string: trimmed text matching `^[+-]?(\d+(\.\d*)?|\.\d+)$` becomes a number through `Number()`; anything else (blank, `1e3`, `1,200`, `10%`, `NaN`, `Infinity`, `∞`) is a field error; `count`, `servers`, `cell_x` and `cell_y` reject fractions; the message names the row and field and quotes the text: `Row 2, count: must be a whole number of 0 or more (got "-5").` (matrix row 13, negative count).
5. THE SYSTEM SHALL report, each naming the row (row 1 for headers) and the field: a duplicated header `Column "start_min" appears twice in row 1.` (matrix row 13); a missing template header `Column "route" is missing from row 1.`; a duplicate ID `Row 3, station_id: "checkin" is already used in row 2.`; an ID outside the engine's `ID_FORMAT` rule (3.9), reported with the engine's message `Row 2, station_id: Station id "a#1" must be 1–64 characters and must not contain "|" or "#".`; a route token naming no station in the imported stations (or, when no `Stations CSV` is given, in the current scenario) `Row 2, route: station "lounge" is not defined.` (matrix row 13, invalid route); a repeated station in a route; more than 6 stations in a route; `arrival_pattern` outside `even` and `uniform`; `start_min`/`end_min` violating `0 ≤ start < end ≤ horizon`; `servers` outside 1–20; service values violating `0 < min ≤ mode ≤ max` `Row 2, service_mode_s: must be between service_min_s (8) and service_max_s (22) (got 30).`; a station cell outside the current grid or on a blocked, entrance or exit cell, or on another station's cell (an editor rule stricter than the validator, 3.5); a station cell with no path from the entrance or to the exit, reported from the validator's `UNREACHABLE` issue (`simulation-contract` 1.8; its `path` is `layout` and it carries no `entity`, so the adapter finds the station through `createPathCache(candidate).unreachable`) mapped to the row, with the engine's message verbatim: `Row 3, cell_x/cell_y: No walkable path between entrance (0,12) and station "packs" (30,4).` (matrix row 13, unreachable station); an issue on a table this import did not supply (a route segment of a current cohort, path `cohorts[i].route[k]`, when only `Stations CSV` is given) listed as `Current scenario, cohort "doors", route: No walkable path between station "checkin" (10,12) and station "packs" (30,4).`; more than 10 stations; and a total `count` above 5,000.
6. WHILE the preview has at least one error THE SYSTEM SHALL disable `Apply import` (`aria-disabled="true"`), show the errors as a text list above the parsed rows with each entry a button that moves focus to the offending row, and keep the current scenario unchanged: the canonical hash in the assumptions panel is identical before and after each of the four matrix-row-13 fixtures.
7. WHEN `Apply import` is activated with zero errors THEN THE SYSTEM SHALL replace in one committed edit the cohorts (when `Arrivals CSV` was given) and the stations (when `Stations CSV` was given), keep `layout`, `id`, `baseSeed`, `horizonMs`, `walkSpeedMps` and `notes` from the current scenario, increment `revision`, label existing results `Stale — rerun` (4.3), close the dialog, move focus to the first changed table and announce `Imported <a> cohorts and <s> stations from <file names>.` in the status region.
8. IF Papa Parse reports an error or the file cannot be read THEN THE SYSTEM SHALL show `Could not read <file name>: <Papa Parse error message or error name>.` in the dialog and change nothing.
9. THE SYSTEM SHALL never fetch a CSV or workbook from a URL, never evaluate a formula, and import only the template columns; a text starting with `=`, `+`, `-` or `@` in `label` is imported as literal text, rendered as text everywhere (9.5) and escaped by the CSV export generator (`escapeFormulae: true`, owned by `paired-comparison-and-release`).

### Requirement 2 — Workbook import and export (xlsx, values only)

**User Story:** As an organizer who keeps assumptions in a spreadsheet application, I want to import the documented workbook template with values only and export the current scenario back to the same three sheets, so that I can edit in my spreadsheet and round-trip without the app ever running my formulas or reading any other sheet.

#### Acceptance Criteria

1. WHEN an `.xlsx` file is chosen (`Workbook (.xlsx)` = `data-testid="import-workbook"`) THEN THE SYSTEM SHALL read it locally with SheetJS Community Edition (Apache-2.0; version pinned at scaffold time; install source *verify* and recorded in `docs/third-party-notices.md`) behind `src/imports/workbookReader.ts`, open only the sheets named exactly `Arrivals`, `Stations` and `Settings`, and state in the preview `Sheets read: <names>. Not read: <other names or "none">.`
2. THE SYSTEM SHALL never read a cell of any other sheet: `tests/imports/xlsx.test.ts` passes a recording `WorkbookReader` whose `sheet(name)` throws for any name outside the three, and the fixture `harbor-hall-extra-sheet.xlsx` (an added `Attendees` sheet with columns `name,email` and two fictional rows) imports with `Attendees` listed under `Not read` and nothing from it in the candidate scenario (matrix row 14).
3. IF `Stations` or `Arrivals` is absent THEN THE SYSTEM SHALL refuse the workbook with `The workbook has no sheet named "Stations". Sheets found: <names>.` and no preview rows (matrix row 14, `harbor-hall-missing-stations.xlsx`); IF `Settings` is absent THEN THE SYSTEM SHALL keep the current `title`, `horizonMs`, `walkSpeedMps` and `baseSeed` and say `Settings sheet not present; current settings kept.`
4. THE SYSTEM SHALL read `Arrivals` and `Stations` with the rules of 1.4 and 1.5 applied per sheet, every message naming sheet and cell as well as row and field (`Stations!C3 (servers): must be a whole number from 1 to 20 (got "two").`), and SHALL read `Settings` as `key,value` rows with keys `title` (text, 1–120 characters), `horizon_min` (0 < value ≤ 360), `walk_speed_mps` (> 0), `base_seed` (text, 1–64 characters); unknown keys are listed as `Settings keys not read: <keys>` and not applied.
5. WHEN a cell carries a formula and a saved value THEN THE SYSTEM SHALL use the saved value, mark the cell in the preview with `formula (saved value used)` and list it under `Formula cells: <sheet!cell, …>`; WHEN a cell carries a formula and no saved value THEN THE SYSTEM SHALL report `Stations!C3 (servers) is a formula with no saved value. Open the workbook, let it calculate, save, and import again.` and `Apply import` SHALL stay disabled (matrix row 14).
6. THE SYSTEM SHALL accept a number from a numeric cell or from a text cell matching 1.4, SHALL report a date, boolean or error cell in a numeric field as `Arrivals!B2 (start_min): expected a number, found a date cell.` (`a boolean cell`, `an error cell`), and SHALL read a numeric cell in a text field (`cohort_id`, `station_id`, `label`, `route`, `arrival_pattern`) as its decimal text.
7. WHEN `harbor-hall.xlsx` is imported into the Harbor Hall baseline THEN THE SYSTEM SHALL produce the same canonical hash as importing `arrivals.csv` plus `stations.csv` into the same baseline, and the same hash as `baseline.json` itself (matrix row 14; `tests/e2e/import.spec.ts` compares the hash text of the assumptions panel).
8. WHEN `Export workbook` (`data-testid="export-workbook"`, rendered only once task 15 has run) is activated THEN THE SYSTEM SHALL call `exportWorkbook(scenario)` of `src/exports/xlsx.ts` (owned by `paired-comparison-and-release`, its 7.5) and save `<title-slug>-<hash8>.xlsx` whose `Arrivals`, `Stations` and `Settings` sheets hold typed values only (numbers as numbers, text as text, no formulas); importing that file into the same layout SHALL reproduce the same canonical hash (the workbook half of the R7 round trip).
9. THE SYSTEM SHALL apply a workbook import atomically as in 1.7, with `layout` kept from the current scenario and with `title`, `horizonMs`, `walkSpeedMps` and `baseSeed` replaced only by the keys `Settings` provides.
10. IF the file is not a readable workbook (the reader throws) THEN THE SYSTEM SHALL show `Could not read <file name> as a workbook: <error name>.` and change nothing; a `.xlsx` larger than 2 MiB is refused per 1.3.

### Requirement 3 — One canonical scenario: tables, floor plan, coordinate form, nudge and delete guard

**User Story:** As an organizer, I want the tables and the floor plan to be two views of the same scenario, so that dragging a station, typing its coordinates and nudging it with the keyboard are the same edit and nothing on screen can disagree.

#### Acceptance Criteria

1. THE SYSTEM SHALL hold exactly one `Scenario` in the editor store (`src/ui/state/store.ts`); the arrivals table, the stations table, the floor plan and the assumptions panel SHALL render from it in the same React commit; `tests/ui/editor-agreement.test.tsx` asserts after every edit kind that the `cell_x`/`cell_y` inputs of a station, the floor plan marker's `data-cell` attribute and `scenario.stations[i].cell` are equal.
2. WHEN a station marker is dragged on the floor plan and dropped on a free in-bounds cell THEN THE SYSTEM SHALL commit `station/move` once on drop (one undo entry), update the marker and the `cell_x`/`cell_y` inputs in the same commit, and announce `Welcome packs moved to (12, 7).` (matrix row 15: drag `packs` to (12,7)); the marker follows the pointer during the drag without committing.
3. WHEN a valid pair is typed into `cell_x` and `cell_y` and committed by Enter or blur THEN THE SYSTEM SHALL move the marker to that cell in the same commit as one undo entry (matrix row 15: type (12,7)).
4. WHILE a station is selected and the floor plan wrapper has focus THE SYSTEM SHALL move that station by exactly one cell per ArrowUp, ArrowDown, ArrowLeft or ArrowRight `keydown` (ArrowUp decrements y), each press one committed edit and one undo entry (matrix row 15: one cell per key press).
5. IF a move by drag, typing or nudge targets a cell outside the grid, a blocked cell, the entrance, the exit or another station's cell THEN THE SYSTEM SHALL leave the station where it is, keep the typed values in the inputs with the inline error `Cell (16, 21) is blocked.` (`is outside the 40 × 24 grid.`, `is the entrance.`, `is the exit.`, `is used by Check-in desk.`), and put the same text in the status region. The occupied-cell rule (entrance, exit or another station's cell) is an editor rule stricter than `validateScenario`, which allows shared cells (`simulation-contract` design, Decisions): a scenario that validates but shares a cell opens, runs and prints, each station on the shared cell shows `Cell (10, 12) is shared with Check-in desk.` beside its `cell_x`/`cell_y` inputs, and no new edit may create a shared cell.
6. WHEN `Delete` is activated for a station that appears in any cohort route THEN THE SYSTEM SHALL refuse with `Check-in desk (checkin) is on the route of cohort "doors". Remove it from the route before deleting the station.` beside the button and in the status region, and the scenario SHALL be deep-equal before and after (matrix row 15: delete `checkin` while routed); WHEN the station is on no route THEN THE SYSTEM SHALL delete it as one committed edit and select nothing.
7. THE SYSTEM SHALL give every floor plan action a form or keyboard equivalent: station cells through the table (3.3); blocked cells through the layout panel's `Blocked cells` list (`Add cell` with `x` and `y` fields, `Remove` per entry) and through Space on the floor plan's cell cursor; entrance and exit through `x`/`y` fields in the layout panel and through `E` and `X` on the cell cursor; grid size through `Columns` and `Rows` fields (1–80 each; shrinking is refused when a removed column or row holds a station, the entrance, the exit or a blocked cell, naming the lowest-numbered such column or row: on the baseline, `Columns` 30 gives `Column 34 is used by Welcome packs.` and `Rows` 22 gives `Row 22 is blocked.`); and Escape while the floor plan wrapper has focus SHALL clear a station or cohort selection to the cell cursor (placed on the deselected station's cell, or kept where it was), so that the arrows move the cursor again (9.3).
8. THE SYSTEM SHALL draw on the floor plan the entrance, the exit, blocked cells, each station as a labelled marker and, for the selected cohort, the computed route polyline read from the engine's path cache: `createPathCache({ layout, stations, walkSpeedMps })` of `src/spatial/path-cache.ts`, held per `cache.key` and rebuilt when the key changes, with `cache.lookup({ kind: 'entrance' }, { kind: 'station', id })` and the following pairs giving `cells`, `distanceM` and `durationMs` for each consecutive pair of `['entrance', …route, 'exit']`; each segment is labelled `<metres> m · <seconds> s`, the metres with at most one decimal (`5 m`, `2.5 m`) and the seconds rounded to one decimal, as a map annotation (Harbor Hall baseline: `5 m · 4.2 s`, `12 m · 10.0 s`, `21 m · 17.5 s`; the run sheet and the timeline carry the exact millisecond value, 8.2); WHEN a pair is listed in `cache.unreachable` THEN it SHALL be drawn as a dashed straight line with the label `no path` and the run is blocked per 4.4.
9. THE SYSTEM SHALL keep IDs as strings obeying the engine's `ID_FORMAT` rule (`simulation-contract` 1.4: 1–64 characters, never containing `|` or `#`), unique per table, editable only in the tables; renaming a station ID SHALL rewrite every route that references it in the same committed edit; a duplicate ID is refused inline with `"checkin" is already used.` and an ID outside the rule with `"a#1" must be 1–64 characters and must not contain "|" or "#".`
10. THE SYSTEM SHALL enforce the plan's limits with inline messages and disabled `Add` buttons: 10 stations (`10 of 10 stations`), 6 visits per route, 80 × 80 cells, 5,000 attendees in total across cohorts, a 360-minute horizon, servers 1–20, walking speed and service durations above 0, whole counts of 0 or more, `0 ≤ start < end ≤ horizon`; the inputs keep the typed value with the error until corrected and the scenario keeps the last valid value.

### Requirement 4 — Undo, redo, stale results and blocked routes

**User Story:** As an organizer trying ideas, I want every committed edit to be undoable and every result to say when it no longer matches the inputs, so that I can explore freely without losing a good layout or trusting a number that belongs to a different scenario.

#### Acceptance Criteria

1. THE SYSTEM SHALL keep an undo stack of at most 100 committed edits (the oldest entry dropped beyond that) and a redo stack cleared by any new committed edit; `Undo` (Ctrl+Z, Cmd+Z) and `Redo` (Ctrl+Shift+Z, Cmd+Shift+Z, Ctrl+Y) SHALL restore the previous or next snapshot deep-equal, increment `revision`, keep the selection when its target still exists, and carry `aria-disabled="true"` when their stack is empty (never the `disabled` attribute).
2. THE SYSTEM SHALL count as one committed edit: a drop (3.2), one nudge press (3.4), one field commit with a changed value, one obstacle toggle, one `Add` or `Delete`, one ID rename, one applied import (1.7, 2.9), one entrance, exit or grid-size change, one scenario JSON open (10.7); keystrokes inside a field, a drag in progress and a field commit with an unchanged value SHALL create no entry.
3. WHEN a committed edit, undo or redo changes the canonical hash of a tab while that tab holds results THEN THE SYSTEM SHALL label every result surface (result tables, game view header, run panel, Print screen) `Stale — rerun` in the same commit and keep the previous results visible and readable (matrix row 17); WHEN a later edit restores the hash of the results THEN THE SYSTEM SHALL remove the label; a change to `title` or `notes` SHALL not mark results stale. Results belong to the tab whose scenario produced them (`results[i]` for `scenarios[i]`): switching tabs shows that tab's results and its label and never relabels another tab's results; opening Harbor Hall and running the baseline, then switching to `Harbor Hall Community Fair: extra check-in staff`, shows that tab with no results and the baseline tab, on return, still `fresh`.
4. WHEN `Simulate` is activated while a route of the current scenario has a segment with no path (a pair of the route's consecutive nodes listed in `createPathCache(snapshot).unreachable`; the segments are checked cohort by cohort in scenario order and, within a route, in route order from the entrance to the exit, and the first one without a path is reported) THEN THE SYSTEM SHALL request no run, show `Run blocked: no path from Check-in desk (checkin) to Welcome packs (packs). Clear a corridor on the floor plan or move a station.` (`from the entrance (0, 12)` / `to the exit (0, 4)` for the first and last segments) in the status region and the run panel, and keep previous results with their `Stale — rerun` label, never replaced or cleared (matrix row 16: every corridor between `checkin` and `packs` blocked).
5. WHEN the current run's handle resolves `{ status: 'error', message }` (the adapter's outcome for a worker `error`, a malformed message or a worker that stopped, `simulation-contract` 9.7, 9.9, 9.11) THEN THE SYSTEM SHALL show `Run failed: <message>` in the run panel and the status region, re-enable `Simulate` and keep previous results labelled stale.
6. THE SYSTEM SHALL show the assumptions panel beside the tables with the fixed assumption text (one FIFO line per station feeding identical parallel servers; routes visit each station at most once; staffing constant through a run; unlimited queue capacity; nobody leaves early; walking at a constant speed along computed grid paths; no personal space, congestion, doorway throughput, accessibility clearance or crowd pressure; results are scenario results under these assumptions, not a forecast), the limits of 3.10, and the lines `Scenario hash: <64 hex>`, `Model version: <modelVersion>`, `Seed: <baseSeed>`, `Horizon: <minutes> min`, updated in the same commit as any edit.

### Requirement 5 — Simulate, progress, cancel and late results

**User Story:** As an organizer, I want one obvious Simulate action with visible progress and a Cancel that answers at once, so that a long run never traps the interface and a result from a cancelled or older run never appears as the current one.

#### Acceptance Criteria

1. WHEN `Simulate` is activated THEN THE SYSTEM SHALL take an immutable snapshot of the current tab's scenario with its canonical hash, check every route segment against `createPathCache(snapshot).unreachable` (4.4), and call `client.run(snapshot, [0], { trace: true, onProgress, onResult })` on the engine's `SimulationClient` (`simulation-contract` 9.1–9.2; the adapter assigns the `runId`, strictly increasing within the session, and returns it on the `RunHandle`); THEN it SHALL keep that handle as the active run, set `Simulate` to `aria-disabled="true"`, show `Cancel` and `Simulating… 0 of 1`, and update the text from `onProgress(done, total)` (the adapter delivers at most 5 per second).
2. WHEN the active handle's `onResult(result)` fires with `result.replication === 0` and `result.scenarioHash` equal to the snapshot's hash THEN THE SYSTEM SHALL store `result` with the snapshot and hash as that tab's results, remove any `Stale — rerun` label, load `result.trace` into the game view at clock 0 and start playback at 1× (paused under reduced motion, 9.4), fill the result tables, and, when `handle.done` resolves `{ status: 'complete' }`, re-enable `Simulate` and announce `Run complete: <admitted> attendees, replication 0, hash <hash8>.` (`drain-capped` results append `; <n> attendees unfinished at the drain cap`).
3. WHEN `Cancel` is activated THEN THE SYSTEM SHALL call `client.cancel()`, show `Cancelling…`, and wait for the active handle's `done`, which the adapter resolves `{ status: 'cancelled', message }` within 250 ms either on the worker's acknowledgement (`Simulation cancelled.`) or after terminating and recreating the worker (`Simulation cancelled. The simulation worker did not respond within 250 ms and was restarted.`; `simulation-contract` 9.4); THEN THE SYSTEM SHALL show `Run cancelled.` in the status region, show the adapter's message verbatim in the run panel, re-enable `Simulate` and keep the previous results and their label unchanged (matrix row 17; `tests/e2e/run-controls.spec.ts` on the 5,000-attendee fixture measures the interval from the Cancel activation to `Run cancelled.` with `performance.now()` and prints it in its output for the task's log row; the 250 ms bound itself is asserted by the engine's `tests/model/worker.test.ts` with fake timers).
4. THE SYSTEM SHALL ignore, with no visible change, any `onProgress`, `onResult` or `done` callback of a handle that is no longer the active one, and any `onResult` whose `result.scenarioHash` differs from the active snapshot's hash (the adapter already drops messages of a non-current `runId`, `simulation-contract` 9.2, 9.6; this is the UI-side guard of matrix row 17): `tests/ui/run-controller.test.ts` drives the controller with the fake client of `tests/ui/fakePort.ts`, starts run 1, cancels it, starts run 2, then fires run 1's `onResult` late and asserts that the reducer received no `run/result` for it while run 2 completes normally (matrix row 17, late result, UI side).
5. WHEN `Simulate` is activated while a run is in progress, or `scenario/select-tab` switches tabs while a run is in progress THEN THE SYSTEM SHALL cancel the current run per 5.3; a new `Simulate` starts its run from the `run/finished` callback of the cancelled one, on the tab that is current at that moment.
6. THE SYSTEM SHALL run the simulation only in the worker: `tests/ui/replay-boundary.test.ts` fails if any file under `src/ui/**`, `src/replay/**`, `src/imports/**` or `src/storage/**` imports a value (anything but `import type`) from `src/simulation/**`, `src/spatial/**`, `src/workers/**` or `src/domain/**` other than `validateScenario` and `MESSAGES` (`src/domain/validate.ts`), `scenarioHash` (`src/domain/hash.ts`), `LIMITS` (`src/domain/limits.ts`), `MODEL_VERSION` (`src/simulation/version.ts`), `formatMetricValue` (`src/simulation/metrics.ts`), `createPathCache` and `describeNode` (`src/spatial/path-cache.ts`) and `createSimulationClient` (`src/workers/client.ts`); WHILE a 5,000-attendee run is in progress THE SYSTEM SHALL handle a DOM click within 200 ms (`tests/e2e/run-controls.spec.ts`, p95 over 10 clicks on the named laptop, a target until recorded).
7. THE SYSTEM SHALL NOT parse, validate or post worker messages itself: message validation, `runId` numbering, the 250 ms terminate-and-recreate rule and the discard of late or malformed messages belong to the adapter (`simulation-contract` 9.1–9.11), and the UI observes only `RunHandle` callbacks and outcomes; one `SimulationClient` is created by `src/app.tsx` (edited by Kiro in task 6) for the whole session and disposed on unload.
